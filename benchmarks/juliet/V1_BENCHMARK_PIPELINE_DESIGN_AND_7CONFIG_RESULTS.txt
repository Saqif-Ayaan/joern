1) Purpose and Scope
--------------------
This document explains the V1 benchmarking pipeline used in this repository and presents a full
results breakdown for the discussed config set on the curated 73-program dataset.

In this document, "V1" means the original flow-level benchmark/scoring path:
- Analysis output generation via run_bof_workflow.sc in source->sink mode
- Function-level evaluation via score_joern_results.py

V1 primary question:
- Does the configured analysis report taint flow at Juliet function-level labels correctly?

V1 is NOT the sanitizer-decision scorer. Sanitizer decision benchmarking is the separate V2 path.

3) V1 Pipeline Architecture
---------------------------
The V1 pipeline is a staged source->sink benchmark pipeline:

A) Subset preparation
- build_juliet_subsets.py builds staged A/B/C subsets and manifests.
- classify_juliet_cases.py labels functions:
  - bad*      => positive (vulnerable expected)
  - goodB2G*  => negative (safe expected)
  - goodG2B*  => excluded from scoring

B) Analysis execution
- run_joern_on_subset.py runs one (stage, config) cell.
- It manages cache for CPG build and run outputs.
- It executes run_bof_workflow.sc with the config policy toggles.
- It writes per-cell artifacts:
  - findings JSON
  - sanitizer decisions JSON (telemetry; not consumed by V1 scoring)
  - metadata JSON
  - logs

C) V1 scoring
- score_joern_results.py consumes findings + labels.
- Matching strategy is function-level with file/function and line-based fallback.
- Per scored function per config:
  - predicted_positive = at least one matched finding
  - actual_positive    = label is "positive" (bad*)
- Confusion matrix semantics:
  - TP: bad* and finding exists
  - FP: goodB2G* and finding exists
  - TN: goodB2G* and no finding
  - FN: bad* and no finding

D) V1 aggregate outputs
- summary.json, metrics.csv, mismatches.csv
- Optional summarize_results.py for multi-run aggregation


4) What V1 Benchmarks (and What It Does Not)
--------------------------------------------
V1 benchmarks:
- End-to-end flow detection quality at function-level labels.
- Whether dangerous flows are reported in bad* and suppressed in goodB2G*.

V1 does not benchmark:
- Whether a specific sanitizer decision at a callsite is correct.
- Whether a discovered function classified as sanitizer is semantically correct.

Those are V2 concerns.

9.3) Interpretation by metric
- TP unchanged (77 -> 77):
  Discovery ON did not add new vulnerable-function hits in this benchmark setting.
  The source->sink coverage for positives remained the same.

- FN unchanged (10 -> 10):
  Discovery ON did not recover missed positive functions in this run.
  This means recall bottlenecks are elsewhere (source/sink reachability and/or flow modeling limits),
  not primarily in sanitizer handling for these cases.

- FP drops strongly (110 -> 20):
  This is the dominant effect. Discovery ON removes many findings on negative (goodB2G) functions
  that OFF mode still reported.

- TN rises symmetrically (13 -> 103):
  This is the complement of FP reduction; negatives are handled more correctly.

9.4) Stage-level contribution for trust on/off
- Current CSV pre-aggregates stage-level numbers in legacy overall mode only.
- For updated FN interpretation, rely on:
  - Section 6 (core-only config metrics),
  - Section 13.3 (explicit list of the 10 persistent core FNs, all in Stage B).

9.5) Why these differences exist in V1 terms
Within V1 (function-level taint outcome scoring), trust_discovery_on changes behavior by allowing
runtime sanitizer discovery to suppress flows in cases where OFF mode keeps them.
In this dataset, that suppression mostly affects negative functions, which manifests as:
- fewer FPs
- more TNs
- no change to TP/FN

So, for V1, the observed gain is specificity-oriented (false-alarm reduction), not sensitivity-oriented.

9.6) Fruitful contribution or fluff?
Short answer for this benchmark slice: fruitful, but narrowly.

Why it is fruitful:
- Large and repeatable FP reduction (-90) with no TP loss.
- Significant precision and FPR improvements.
- Practical analyst impact: fewer false alarms to triage for equivalent positive coverage.

Why it is not a complete win:
- Recall does not improve (FN unchanged at 10 in core-only view).
- Discovery ON alone does not solve missed-vulnerability coverage.
- V1 cannot prove sanitizer decision correctness directly; it only shows downstream flow outcomes.

Final assessment:
- Not fluff: there is measurable, material benefit in false-positive control.
- Not sufficient alone for full research claim: pair this with V2 sanitizer-decision correctness
  analysis to demonstrate that the FP reduction is both effective and semantically justified.

14) Standalone: How the Clamp-Focused Subset and Clamp Helpers Were Built
--------------------------------------------------------------------------
This section documents the data-construction pipeline behind the clamp-focused benchmark
population used in this doc.

14.1) Source corpus and Stage A/B/C staging
- Source: local unpacked Juliet C/C++ tree (`CWE121` + `CWE122`).
- Script: `benchmarks/juliet/scripts/build_juliet_subsets.py`.
- Output staged roots:
  - `benchmarks/juliet/outputs/staged/A`
  - `benchmarks/juliet/outputs/staged/B`
  - `benchmarks/juliet/outputs/staged/C`
- Staging behavior:
  - files are grouped by Juliet family id (multi-file variants stay together),
  - stage assignment by variant:
    - A = `01`
    - B = `01..22` and `31..45`
    - C = remaining
  - stage trees are materialized as symlinks to source files.

14.2) Function labels used by transformation and scoring
- Script: `benchmarks/juliet/scripts/classify_juliet_cases.py`.
- Label contract:
  - `bad*` and name patterns with `_bad_` => `positive`
  - `goodB2G*` and name patterns with `_goodB2G` => `negative`
  - `goodG2B*` => `exclude`
- These labels are consumed both by transformation targeting and by V1 scoring.

14.3) Clamp helper synthesis and sink rewrite mechanics
- Script: `benchmarks/juliet/scripts/transform_stage_a_clamp_dataset.py`.
- Despite name, script is reused for A/B/C by passing stage-specific manifests and roots.
- Stage outputs:
  - Derived trees:
    - `benchmarks/juliet/outputs/derived/A`
    - `benchmarks/juliet/outputs/derived/B`
    - `benchmarks/juliet/outputs/derived/C`
  - Transformation manifests:
    - `benchmarks/juliet/manifests/stage_a_clamp_transform_manifest.json`
    - `benchmarks/juliet/manifests/stage_b_clamp_transform_manifest.json`
    - `benchmarks/juliet/manifests/stage_c_clamp_transform_manifest.json`

Transformation logic per function:
- Target only functions labeled `positive` or `negative`.
- Find sink candidate in function body by assignment pattern:
  - `array[index] = ...`
- Infer fixed array size from local declaration before sink:
  - e.g., `int buffer[10]` => upper index `9`.
- Find nearest preceding `if (...)` condition and parse recognized guarantees.

Guard parsing currently recognizes:
- lower-bound guarantee:
  - `index >= 0` or `0 <= index`
- upper-bound guarantee:
  - `index < N` (treated as safe upper guarantee only when `N == array_size`)
  - `index <= N` (treated as safe upper guarantee only when `N == array_size - 1`)

Helper generation:
- Per rewritten sink, generate two static helpers:
  - `clamp_bad_<function>_<sinkLine>`
  - `clamp_good_<function>_<sinkLine>`
- `clamp_bad_*` encodes only guarantees parsed from the original guard.
- `clamp_good_*` always enforces full bounds `0..array_size-1`.

Rewrite rule:
- Rewrite only sink index expression, not surrounding guard/control-flow.
- Example shape:
  - before: `buffer[data] = 1;`
  - after : `buffer[clamp_bad_...(data)] = 1;` for positive function
  - after : `buffer[clamp_good_...(data)] = 1;` for negative function
- Generated helper blocks are inserted near top-of-file (after includes).

Non-rewritten decisions are tracked with explicit reasons:
- `no_assignment_array_index_sink_in_function`
- `unable_to_infer_fixed_array_size`
- `no_guard_condition_found_before_sink`
